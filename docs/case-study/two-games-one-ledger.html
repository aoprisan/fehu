Case study · fehu

Two Games, One Ledger

A Rust multiplayer shooter and a client-only browser city-builder share nothing — not a language, not a runtime, not a genre, not a player. They arrived at the same hole in the same place, and the fix has the same shape in both.

Subject fehu · the economy library and its server
Cases DeadCity, Global Conflict v2
Level High-level; the design notes are linked at the end
The premise

Every game with a currency eventually needs a ledger. Almost none of them start with one.

A currency starts as a number that goes up. It stays that way through the prototype, through the vertical slice, and usually through launch, because a number that goes up is correct right up to the moment somebody else can affect it. Then, in a fairly narrow window, three things become true at once: players notice inflation before you do, retries pay twice, and the feature you actually want to build turns out to be a feature about ownership.

These two projects are at that window, from opposite directions. Looking at them side by side is useful precisely because they have nothing in common — which makes the parts that are in common the interesting ones.

The finding

The same hole, wearing two different costumes.

Both were found the same way: by asking what statement about money the code could be wrong about. In both, the answer was none.

DeadCity 
// grant, in effect
agent.attrs[SC] += amount;
// persistence
File::create(path).unwrap();
write_all(&whole_state);   // on a timer

Nothing conserves, so a payout bug and a popular weekend look identical on every graph that exists. A crash between grant and save loses the grant; a client that reconnects and re-sends a claim is paid twice, held off only by an in-memory flag.

No supply statement · no durability · no transfer
Global Conflict v2 
// game/market.ts
city.cash += n * resourceInfo(r).sell   // sell
city.cash -= n * resourceInfo(r).buy    // buy

Money is created by selling and destroyed by buying. There is no supply at all — not an unenforced one, an absent one. With one player that is invisible. With two it is the whole game: the equilibrium price of all 129 goods is set by how much money exists.

Money from nowhere · save file owned by the player

One had a ledger with no audit. The other had arithmetic where the ledger should be.

The instrument

What fehu contributes, in four sentences.

Money is an integer count of cents in one world-wide ledger, and every movement is a set of signed postings that sums to zero — so Σ balances = minted − burned is an audit anyone can run, and no route a player can reach changes the supply. Goods are issued and consumed rather than floated, and the audit asks the strict question: every issued unit that has not been consumed is held by somebody. Nothing changes the world except a journaled command, appended and fsynced before the response goes out, replayed on start-up through the same code the live path uses. And a game backend holds a scoped service credential — provision, reward, inventory, events — rather than the key that can mint.

The library underneath (crates/fehu) is no_std + alloc and bit-reproducible on native and wasm32, which turns out to matter for exactly one of these two cases — and matter a lot.

The divergence

Same instrument, two quite different instruments panels.

This is the part worth reading if you are evaluating fehu for something else. The economics are identical; almost every engineering decision around them differs, and the differences are all downstream of two questions — who is allowed to be authoritative, and how fast is the hot path.

The convergence

Both obey one rule, at rates two orders of magnitude apart.

A journaled ledger that fsyncs before it answers is the right instrument for money and the wrong instrument for a game loop. Every workable integration therefore has the same shape: the fast thing accumulates in memory, and a natural boundary in the game — not a timer someone picked — decides when it crosses.

What generalises

Five things that came out of both, not one.

Settle at a boundary the game already has

Run end and page hide are not arbitrary flush points — they are moments where the player already understands that something has concluded. Pick those and the failure semantics explain themselves; pick a timer and you have to invent a story about the last four seconds.

Move property. Leave progress alone.

XP, levels, energy and season points have no scarcity, no owner-to-owner transfer and no inflation risk. Putting them in a ledger costs a round trip and buys nothing. Both integrations moved less than half of what looked at first like “the economy”.

Idempotency belongs on the game’s own event id

A transport-level key protects against a lost response. A key on run:8f2c1a or season:7:tier:12 protects against the same event being reported twice by two different paths a year apart — which is the failure that actually happens.

Randomness stays upstream

A ledger that replays its journal cannot roll dice. Crate contents, loot tables and drop rates stay in the game, and only the outcome is recorded. This is a constraint that reads as a limitation and behaves as a clarification.

Migration cost is set by one question

Can you reset the world? Global Conflict can, and already does on every config change, so its migration is free. DeadCity cannot, so its cutover is a deliberate mint with a number written down. Nothing else about the two integrations differs by as much.

Where each lands

Different asks, for the same reason.

DeadCity

A two-week shadow spike

Provision on login, settle one district’s runs into fehu at run end, and let the attributes keep deciding what the player sees. Diff the two nightly for a week.

If they agree, the rest is a phase plan with one one-way door. If they disagree, that is a payout bug which has been invisible until now — which is itself the result, and the cheapest way this project will ever find it.

Global Conflict v2

One sprint, six methods

The seam already exists: GameClient.ts was written with a second implementation in mind and says so. Implement six market methods against fehu, delegate the rest to the existing mock, gate it on a build-time host.

With no host configured the Pages deploy is unchanged. The demo is two browsers trading with each other — the first thing this game has ever done that needed two.
